Assembly

Construction: strategies, tree building, the cores and workspaces, and the BEAST far-field assembler.

MLFMA.Assembly — Module
MLFMA.Assembly

Build MLFMA maps from operators, spaces and trees.

This top layer owns the BEAST-facing far-field assembler, store logic, collection builders, MLFMAStrategy family, Galerkin and Petrov cores, and map constructors.

Collection builders choose the assembler, collection family, side and storage. The collection types and their multiply kernels belong to FarFields, which does not depend on this layer.

dummyfarfieldassembler.jl belongs to TestSupport: it uses BoxFarFieldSampling and leafids from this layer, but this layer does not depend on it.

MLFMA.Assembly.NEARINTERACTIONSQUADSTRATEGYRECOM — Constant
NEARINTERACTIONSQUADSTRATEGYRECOM

The recommended BEAST quadrature strategy for near interactions.

A DoubleNumWiltonSauterQStrat for singular and near-singular double integrals over 3-D surface elements. This recommendation suits 3-D Maxwell problems, not every geometry. The explicit type checks the constant at load time. Use nearinteractionsquadstrategy to select the operator-dependent default, including BEAST's quadrature for 2-D Helmholtz operators.

MLFMA.Assembly.PROTRUSIONCAP — Constant
PROTRUSIONCAP

The largest protrusion levelprotrusions passes on for grid sizing, 0.25.

Protrusion is normalized by box edge length, so 0.25 means an overhang of a quarter edge and limits linear enlargement to 1.5x. H2Trees warns above 0.5; boxes that small relative to their elements usually need rebuilding rather than higher sampling rates. A λ/12-box tree on a λ/6 mesh measured 1.007, which would otherwise request roughly 3x enlargement.

Ordinary sphere fixtures with the default protrusion check measured maxima around 0.24. The cap bound the fixtures built with NoProtrusionCheck(). It complements the λ/4 halfsize warning in MLFMA.checkboxsizes, but cannot repair unsuitable tree geometry.

MLFMA.Assembly.SHEANALYSISMARGIN — Constant
SHEANALYSISMARGIN

Degrees added to a level's L when choosing its analysis order, 2.

L is not an upper bound on P: a basis function's support can extend beyond its box. The margin allows for this and for the round-off plateau in the coefficient tail. It is a heuristic. shecollections raises if the selected order reaches the analysis order.

MLFMA.Assembly.AbstractAssembledFieldCollectionBuilder — Type
AbstractAssembledFieldCollectionBuilder <: AbstractFieldCollectionBuilder

A builder that owns an assembler: it carries side, assemblerbuilder and quadstrategy, and gets the three accessors and buildfarfieldassembler from those fields. A compressed builder adds an ε, and overrides buildfarfieldassembler only if it assembles something other than what the operator itself radiates, as the two harmonic ones do.

Separate from AbstractFieldCollectionBuilder so that LazyReceiveFieldCollectionBuilder, which is fieldless and has no assembler at all, does not inherit accessors it cannot answer. Under one supertype it would, and asking it for its quadrature would fail with "type has no field quadstrategy" rather than saying that the operation is not part of the lazy protocol. test/FarField/collectionbuilders.jl pins the MethodErrors.

MLFMA.Assembly.AbstractCompressedFieldCollectionBuilder — Type
AbstractCompressedFieldCollectionBuilder{Side} <: AbstractAssembledFieldCollectionBuilder

A builder whose leaves store harmonic coefficients rather than samples: it assembles, analyses the patterns to a per-level order, and returns one collection per leaf.

Parameterized by Side because both sides need it. The radiation and receive bodies are the same three steps and differ only in the per-leaf wrapper, so with the side in the type they become two shared methods plus two small per-builder hooks:

  • analysecollections, the analysis this storage performs;
  • assembledreceivecollectiontype, the wrapper its assembled receive side puts on.

Both hooks use dispatch rather than function-valued arguments.

MLFMA.Assembly.AbstractFieldCollectionBuilder — Type
AbstractFieldCollectionBuilder

Construction policy for one side's field collections: everything buildfieldcollections needs beyond the tree, the operator and the space.

The subtypes share a construction protocol, not a set of fields. AbstractAssembledFieldCollectionBuilder owns an assembler and carries side, assemblerbuilder and quadstrategy; LazyReceiveFieldCollectionBuilder is a concrete builder that has no fields and assembles nothing. Fields and their accessors therefore belong to the assembled subtype, not this supertype.

A new leaf storage supplies its construction policy; iteration and wiring are shared.

AbstractFieldCollectionSide

Which side of an operator a leaf field collection represents: RadiationSide, ReceiveSide or LazyReceiveSide.

MLFMA.Assembly.AbstractLeafStorage — Type
AbstractLeafStorage

How a leaf stores its basis-function far-field patterns: SampledLeafStorage, SphericalHarmonicLeafStorage, VectorSphericalHarmonicLeafStorage or CircularHarmonicLeafStorage.

Independent of AbstractFieldCollectionSide, which identifies the pattern, and chosen per side: FarFieldStrategy carries a trialleafstorage and a testleafstorage, because a Petrov map's test side is assembled over its own space and nothing ties its storage to the trial side's. A LazyReceiveSide is the exception and has no storage of its own: it is derived from the radiation collections, so it follows whatever they are, which is why GalerkinMLFMA requires the two settings to agree (assertsingleleafstorage).

Storage policies select the assembler, collection type and leaf scratch by dispatch. Some harmonic policies assemble Cartesian components instead of using the operator's own store rule.

MLFMA.Assembly.BEASTFarFieldAssembler — Type
BEASTFarFieldAssembler(operator, space, quadstrategy, storerule, ::Type{F})

Assembles a leaf's basis-function far-field patterns by calling BEAST.

Carries the target far-field type F: the component count is derived from it via fielddim, so the two can never disagree, and a caller can ask an assembler which collection type to wrap its output in. A bare count could not answer that, since two representations can share one.

storerule and farfieldtype are independent axes and both must be given. The first is how BEAST's raw value is projected into the moment; the second is what layout the moment has. Neither derives from the other, since ScalarFarField is reached both by radial projection and by storing as is.

Neither has a constructor default. Obtain them from farfieldstorerule(op) and farfieldtype(op) for the operator being assembled.

MLFMA.Assembly.FarFieldStorer — Type
FarFieldStorer(rule, Fs, samplinginfo)
FarFieldStorer(rule, Fs, leafsamplings, tree)

The single H2Factory.AbstractStorer for MLFMA's far-field assembly: a projection rule plus the moments it writes into, the leaf-local index map, and the rule's frame cache.

The (v, ::Nothing, m, n) and (v, cluster, m, n) methods resolve the moment block and its indices. Each rule's _store! method performs the projection.

The three-argument form is the flat, non-tree path: one global moment block, no leaf-local renumbering (indexinleafbox === nothing). The four-argument form is the tree path: one block per leaf, indexed by cluster.

MLFMA.Assembly.FarFieldStrategy — Type
FarFieldStrategy(; assemblerbuilder=FARFIELDASSEMBLERBUILDERRECOM,
                   quadstrategy=FARFIELDQUADSTRATEGYRECOM,
                   leafstorage=LEAFSTORAGERECOM,
                   trialleafstorage=leafstorage, testleafstorage=leafstorage)

Leaf far-field assembly: which assembler builder, its quadrature, and how the assembled patterns are stored. Far-field quadrature is a single numerical rule (BEAST.SingleNumQStrat) rather than the near block's Wilton/Sauter machinery, because leaf far fields have no singular pairs, which is why it is a separate choice from the near-interactions strategy rather than one shared quadrature setting.

Unlike the near side, MLFMA's far-field assembly is its own (BEASTFarFieldAssembler, DummyFarFieldAssembler) with no H2Factory strategy protocol to dispatch through. The selection is therefore a builder object, BEASTFarFieldAssemblerBuilder or DummyFarFieldAssemblerBuilder. This keeps the field's type concrete and lets alternative builders carry construction state.

The leaf storage is an AbstractLeafStorage, SampledLeafStorage, SphericalHarmonicLeafStorage, VectorSphericalHarmonicLeafStorage or CircularHarmonicLeafStorage, and selects what the assembled patterns are kept as. It sits here rather than on its own strategy because it is not independent of the two fields above: the compressed paths substitute a store rule into the same assembler builder and analyse at the same quadrature, so the three choices are one policy. It changes storage only, the direction grids, the translation and the interpolation are identical either way.

One Storage Per Side

trialleafstorage and testleafstorage are separate fields; leafstorage= is a shorthand setting both, which is the common case and what every call site that does not care should keep writing. The two are independent because a Petrov map's test side is ASSEMBLED in its own right, over a different space, so nothing forces it to be stored the way the trial side is:

FarFieldStrategy(; trialleafstorage=CircularHarmonicLeafStorage())          # compress trial only
FarFieldStrategy(; leafstorage=CircularHarmonicLeafStorage())               # compress both

A Galerkin map must have equal settings. MLFMAStrategy does not check this because the strategy does not know which map will consume it. GalerkinMLFMA raises; see assertsingleleafstorage. Its test side is mirrored rather than assembled, so a distinct testleafstorage would have nothing to act on, and silently accepting a knob that does nothing is worse than refusing it.

Use trialleafstorage or testleafstorage to read a side's setting; there is no side-independent leafstorage(strategy) accessor.

The three collection builders derived from this, radiationfieldcollectionbuilder (trial), receivefieldcollectionbuilder (test), lazyreceivefieldcollectionbuilder, are what the map constructors actually consume.

MLFMA.Assembly.LevelTransferStrategy — Type
LevelTransferStrategy(operator; Interpolator=..., PhaseShifter=PHASESHIFTERRECOM)

The child-to-parent level transfer: interpolation between direction grids, and the level phase shift.

Interpolator defaults to interpolatorrecom(operator), INTERPOLATORECOM{15,…} for a 3-D operator and the circular family for a 2-D one, in both cases parameterized by the operator's own γ type, so a real-γ operator cannot silently get a complex interpolator or the reverse. The interpolation trait is not a field: it is read from the operator at construction time and both map constructors error() if the interpolator disagrees, since a mismatch would apply a different component-sign convention than the interpolator it wraps.

MLFMA.Assembly.MLFMAStrategy — Type
MLFMAStrategy(operator, testspace, trialspace=testspace; ...)

Bundle of every construction choice an MLFMA map makes. trialspace defaults to testspace for the Galerkin case; a Petrov-Galerkin map passes both explicitly.

Each sub-strategy is overridable on its own, and overriding one leaves the rest at their defaults:

strategy = MLFMAStrategy(
    operator,
    space;
    farfieldstrategy=FarFieldStrategy(; quadstrategy=BEAST.SingleNumQStrat(1)),
)

MLFMA-specific sub-strategies: TreeStrategy, SamplingStrategy, FarFieldStrategy, LevelTransferStrategy, I2OTranslationStrategy. The near side is H2Factory's: nearinteractionsstrategy is an H2Factory.AbstractNearInteractionsStrategy (see SparseBEASTNearInteractionsStrategy) and nearfieldstrategy an H2Factory.AbstractInteractionStrategy, so isnear, aggregationmode, translatingnodesiterator and aggregatenode are read with H2Factory's accessors applied to nearfieldstrategy rather than with MLFMA ones.

scheduler is normally a bare scheduler rather than a materialized ExecutionScheduling: MLFMA schedules per operation and per level, so the containers have to be keyed by the tree's actual level indices, which are not known until the tree exists, and a strategy is built before the tree. The map turns it into an ExecutionScheduling via executionschedulingfor. Defaulting to a ready-made ExecutionScheduling is what would let a scheduling sized for one tree be handed to another, whose deepest level then has no scheduler entry and throws a KeyError mid-traversal.

A ready-made ExecutionScheduling is rejected at construction because it may cover another tree's level range. H2Factory returns an existing scheduling unchanged, so an explicit check is needed to prevent a later KeyError on an uncovered level.

operator, testspace and trialspace determine the default near-interaction quadrature. The other defaults use the operator or fixed recommendations.

MLFMA.Assembly.SamplingStrategy — Method
SamplingStrategy(operator; samplingbuilder=samplingbuilderrecom(operator), ϵ, protrusionaware)

The same strategy, with the sampling family derived from the operator rather than defaulted to the spherical one.

Which grid an operator radiates onto is a property of its geometry, not a preference: a 2-D Helmholtz operator needs directions on a circle, and handing it the spherical default produces grids the 2-D translation operator and interpolator cannot consume. MLFMA.Assembly.SamplingStrategy — Method
SamplingStrategy(; samplingbuilder, ϵ, protrusionaware=false)

protrusionaware sizes each level's direction grid from the box that contains its basis functions rather than the nominal box. See MLFMA.Assembly.protrudedhalfsize. Basis functions are filed under the box their centre falls in and their supports hang over the faces, so the nominal box understates the angular bandwidth whenever elements are not small compared to boxes. Measured protrusion is 5-25 % of the edge length on ordinary sphere fixtures and raises L by 1-3 at every level, giving roughly 1.5x as many directions at the leaf.

Defaults to false. Enabling it grows the grids and changes accuracy, memory use and runtime; changing that default requires measurements across the supported configurations.

MLFMA.Assembly.VectorSphericalHarmonicLeafStorage — Type
VectorSphericalHarmonicLeafStorage()

Store each leaf's patterns as tangential vector spherical-harmonic coefficients: the X/Psi families rather than three Cartesian scalar expansions. Like SphericalHarmonicLeafStorage it changes storage only; the grids, the translation and the interpolation are untouched.

Compresses further than the Cartesian expansion does, and by more than the coefficient count 2P(P+2) against 3(P+1)^2 predicts (measured 0.500x at e = 1e-3, 0.519x at 1e-4 and 0.660x at 1e-5, because the tangential basis also needs a lower degree). See sphericalharmonics/vectorharmonics.jl for the reason and for the caveat that the advantage narrows as the tolerance tightens.

It also removes the frame projection from the leaf multiply outright: X and Psi are already tangential, so synthesis writes the moment's own two components with no Cartesian stage.

MLFMA.Assembly._buildi2ochannel — Method
_buildi2ochannel(core)

The H2Factory.buildi2ochannel hook for both MLFMA cores.

Goes through H2Factory's own i2ochannels(translation, translatingplan) seam rather than re-running the translation constructor for the second return value the core constructors discard. Both of MLFMA's current I2O collections need no scratch at all, H2Factory.I2OTranslationCollection and DummyTranslationCollection each return EmptyChannels() alongside themselves, because a diagonal translation has nothing to buffer, and i2ochannels(::Any, translatingplan) = EmptyChannels() is exactly that answer. Going through the seam rather than hardcoding EmptyChannels() means a future accelerated I2O (the H2Toeplitz route defines its own i2ochannels method, and its FFT plans MUST be per workspace) is picked up without this hook changing.

Shared by the two cores because the translating plan is derived the same way for both: the trial aggregation and test disaggregation plans, which is the pair H2Factory.I2OTranslationCollection itself reduces to a translating plan.

MLFMA.Assembly._indexchunks — Method

MLFMA.Assembly.protrudedhalfsize — Method
protrudedhalfsize(halfsize, protrusion)

Return the halfsize needed to contain a group's basis functions, using H2Trees' protrusion measure.

H2Trees.levelprotrusions reports (|v - center| - halfsize) / (2 * halfsize) maximised over support vertices and coordinates. This is the excess beyond a box face, normalized by edge length. So the containing box is halfsize * (1 + 2 * protrusion).

A group's angular bandwidth depends on source distance from the expansion centre, not nominal box size. Basis functions are assigned by their centres, but their supports may extend beyond the faces. The adjustment can change the required order substantially. Measured examples:

mesh λ/8, leaf λ/4     protrusion 0.208 at the leaf level, L = 13 -> 16
mesh λ/10, leaf λ/4    protrusion 0.197 at the leaf level, L = 13 -> 16
mesh λ/10, leaf λ/12   protrusion 0.250 at level 4,        L = 10 -> 13

Protrusion grows as boxes shrink: one tree measured 0.052 / 0.104 / 0.208 across three levels. A fixed-size element occupies more of a smaller box, so ignoring its support can undersample deeper levels.
